## 第一优先：实证比较与失败模式

### #1 Single-Round Vector RAG vs an LLM-Compiled Wiki（预注册比较）

- **来源**：arXiv:2605.18490（v1 2026-05-18，v3 2026-10-02）
- **作者/机构**：Theodore O. Cochran（独立研究者，单作者；预注册于 OSF，DOI 10.17605/OSF.IO/ZEMHP）
- **一句话结论**：预注册比较显示，wiki 跨论文综合显著更强、RAG 单点事实查询更稳，但 **wiki 每次查询耗约 21 倍 token，不存在回本点**；谁赢取决于检索基线、评分方法和裁判——综合能力、引用支持、成本必须分开报告。
- **方法要点**：
  - 24 篇论文的小型多域研究语料，13 个评估问题、6 个任务层级（tier）；同一答案模型（Claude Opus 4.7）同时为两个系统答题；双盲 LLM 裁判（GPT-5.4 + Gemini 2.5 Pro）；三个预注册假设 H1 综合 / H2 单点事实 / H3 成本。
  - v3 修正了 v1/v2 的一个评分器截断错误（RAG 证据被截到 1500 字符），**修正后早期版本声称的 wiki 引用支持优势不成立**——该论文自己撤回过一次结论，方法论上非常诚实。
- **关键数字**（部分来自正文片段）：
  - H1（综合）：wiki 在 inter_paper_mapping 上领先 +6.625，但合并双裁判后低于预注册 +2.0 阈值 → **弱支持**。
  - H2（单点事实）：RAG 通过注册检验，但对裁判高度敏感（最大单点分歧：GPT-5.4 评 RAG=9/wiki=6，Gemini 评 RAG=4/wiki=10）。
  - H3（成本）：摄入侧 wiki 904,884,660 tokens vs RAG 1,401,996（**645 倍**，注意 wiki 侧遥测含缓存写入）；查询侧反向：wiki 每查询多花约 **21 倍**，交叉点公式分母为负（-121,020/查询）→ **数学上无回本点**，H3b 被驳回。
  - 分解式 RAG（decomp-RAG）：把问题分解后再检索，以更低 token 成本消除 wiki 大部分综合差距；decomp 答案 94.4% 带引用 vs 单轮 RAG 88.0% vs wiki 76.3%。
  - 裁判排名一致性：整体 groundedness 上 **rho = 0.04**（近乎零）vs 最具体可定义标准上 rho = 0.81。
  - 延迟：RAG 总计 3.3 分钟 vs wiki 22.0 分钟（6.6×；墙钟比 token 比小）。
  - 成本-质量散点：RAG 簇（≤8k tokens，3.75–8.25 分）与 wiki 簇（30k–210k tokens，6.75–9.25 分）**互不帕累托支配**；4/13 个问题上 RAG 以数量级更低的成本打平或胜出。
- **对我们项目的启示**：
  1. **"编译一次、查询变便宜"的摊销叙事在 agent 浏览式查询下不成立**——查询贵在多轮工具调用。查询侧成本必须作为一等设计目标（见 #4 渐进披露、#10 路由加速两条工程出路）。
  2. RAG 加上查询分解就能拿到大部分综合收益。我们必须想清楚 wiki 的差异化价值：**跨源综合的组织结构、人类可读可编辑、长期复利**，而不是单次问答质量。
  3. 小语料（24 篇）上 RAG 够用；wiki 的价值主张应该锚定在语料增长之后。
  4. 评估必须分维度报告，且**自动评分器要有人类标注校验**（该论文的 v3 修正就是活教材）。
  5. 单作者、单模型、小语料——外推需极谨慎，但它是目前唯一预注册的正面比较。

### #2 Does the Wiki Grow Smarter?（已撤稿，负面结果）⚠️

- **来源**：https://www.scierxiv.com/article/scierxiv202605.0291.v1
- **状态**：**2026-11-04 检索时已被作者从 SciEiRxiv 撤回**（页面仅存 "The authors have requested that this preprint be removed from ScieRxiv"）；web 搜索未找到镜像、缓存或转投版本。撤稿原因不明。
- **以下内容来自任务简报，属二手信息，未经一手验证**：
  - 在"异常密集决策任务"上 wiki 不敌 RAG 的**负面结果**。
  - 提出**三种维护者（maintainer）退化模式**：
    1. **fragmentation（碎片化）**：同一主题分散到多个页面，检索时无法聚合；
    2. **atomization（原子化）**：过度切碎，页面失去综合语境；
    3. **over-merging（过度合并）**：不相干内容挤进同一页面，稀释信噪比。
- **即使撤稿仍值得记录的原因**：其结论与 #1（wiki 组织优势弱于预期）、#3（缺陷复合）、#5（千文件崩坏）**互相独立印证**，构成"结构性衰减是模式核心风险"的证据链。
- **后续行动**：如主会话存有该 PDF 或知道作者去向，可补一手验证；引用其结论时必须注明"已撤稿预印本，未验证"。
- **对我们项目的启示**（基于简报内容）：
  1. **页面粒度治理是核心工程问题**：什么时候开新页、什么时候拆、什么时候合并，需要写入 schema 的显式规则 + lint 检测项（fragmentation/atomization/over-merging 三个方向都要查）。
  2. "异常密集决策任务"提示：wiki 综合页会**稀释事实密度**——高密度事实查询场景必须能从 wiki 页下钻回 raw 源（与 #5 的 span 指针、#9 的层级路由呼应）。
  3. wiki 不该是唯一答案：查询路由应能判断"这题该查 wiki 还是查 raw/向量索引"。

### #3 DeepRefine: Agentic Knowledge Refinement via Reinforcement Learning

- **来源**：arXiv:2605.10488（v1 2026-05-11，v2 2026-08-23）
- **作者/机构**：Haoyu Huang, Jiaxin Bai, Shujie Liu, Yang Wei, Huihao Jing, Hong Ting Tsang, Yisen Gao, Zhongwei Xie, Yufei Li, **Yangqiu Song**（香港科技大学 HKUST，宋阳秋组，10 人）
- **一句话结论**：用 RL 训练 agent 对预构建知识库（显式包含 **LLM-Wikis**）做"多轮交互 → 溯因诊断 → 定位缺陷 → 定向修复"的增量精炼，随用户查询持续进化知识库质量，下游任务一致提升。
- **方法要点**：
  - 知识库三类系统性缺陷：**不完整**（缺证据、缺跨文档链接）、**不正确**（低置信/不精确断言）、**冗余**（歧义、共指未解析）——且**缺陷在迭代使用中复合放大**，损害检索保真度与下游表现。
  - DeepRefine 与 KB 多轮交互，对交互史做**溯因诊断（abductive diagnosis）**，定位疑似缺陷，执行定向修复动作做增量更新。
  - **Gain-Beyond-Draft（GBD）奖励**：无需黄金修复轨迹，以"修复后超越草稿的下游增益"为奖励，端到端 RL 训练推理过程。
- **关键数字**：摘要未给具体值（"consistent downstream gains over strong baselines"），需读全文。
- **对我们项目的启示**：
  1. 确认结构性衰减真实且会**复合**——我们的维护回路不能只靠 ingest 时预防，要有**查询驱动的修复**（查询失败 → 诊断 → 修复页面）。
  2. GBD 思路极好："修复的价值 = 修复后能否答对之前答错的问题"。我们的 lint 可以采纳：**修复的验收标准是下游问答回归，而非静态质量分**。
  3. RL 训练对个人项目太重，但"诊断 → 定位 → 修复"的 agentic 工作流可以用提示工程 + 规则复现。
  4. 其缺陷分类（不完整/不正确/冗余）可直接作为我们 lint 的检查清单骨架。

### #4 Progressive Disclosure for LLM-Maintained Wiki Knowledge Bases（预注册消融）

- **来源**：arXiv:2607.04576（v1 2026-07-06，v2 2026-10-07；OSF 预注册 DOI 10.17605/OSF.IO/FEKA7）
- **作者/机构**：Theodore O. Cochran（与 #1 同一独立作者）
- **一句话结论**：在真实 **709 页** LLM 维护的 markdown wiki 上做预注册消融：改造成"紧凑目录 + 单行页摘要 + 按需打开页面"的渐进披露结构后，**所有测试条件下成本明确下降（任务简报称 33–50%，摘要原文未给百分比），答案质量在预设边际内不降**——但论文诚实列出两个限制。
- **方法要点**：
  - 4 个仅在"agent 如何到达页面"上不同的版本（页面内容完全一致，差异只来自访问结构）；3 种测试方式：agent 按固定协议 / 自主选路 / 强制先读目录；跨模型家族裁判盲评 + 对照已验证参考答案 + 人工评分者。
  - **关键预实验发现（反直觉）**：能力强的 agent **根本不加载大索引**——它从问题直接推断页面在哪并直接读取。原本要测的"省索引 token"对这些 agent 不存在，于是把主要结局改为答案质量。
- **关键数字**：
  - 709 页真实 wiki；质量在预设边际内持平（改造版 vs 原版）。
  - 限制一：人工评分者与模型裁判的一致性**远低于计划要求**，质量结论主要依赖裁判 + 敏感性检查。
  - 限制二：**强制先读目录**时、以及两个最可靠评分标准在更严格检验下，质量"未被证明"保持（注意是未证明，不是证伪）。
  - 改造版引用页面更少、每答案工具轮次更少。
  - 成本降幅 33–50% 来自任务简报，摘要只说 "Cost fell clearly in every condition"，**精确百分比待全文核实**。
- **对我们项目的启示**：
  1. index.md 的正确形态不是一次加载的全量目录，而是**三级结构：紧凑目录 → 每页一行摘要 → 按需打开**。
  2. 反直觉发现同样重要：强 agent 会跳过索引直接猜路径 → **页面命名/路径必须语义化、可预测**（与 #10 WikiKV 的 path-as-key 相互印证）。
  3. 渐进披露是控制 #1 中"查询侧 21 倍开销"的直接工程手段，且质量代价未被证明存在。
  4. 与 #1 同样暴露评估痛点：人工与裁判一致性低，质量结论的置信度上限被测量工具卡死。

### #5 The Provenance-First Wiki（千文件崩坏与五个不变量）

- **来源**：Zenodo record 21871213（v1.0.4，2026-08-10，DOI 10.5281/zenodo.21871213；注意 GitHub README 标注的另一 DOI 10.5281/zenodo.21862190 应为早期版本，同一项目）；GitHub: AbleVarghese/Provenance-First-Wiki（本笔记额外抓取了 README 全文，信息量大）
- **作者/机构**：Able Varghese（多伦多，独立研究者；7 star / 1 fork，小众但论证极扎实）
- **一句话结论**：**LLM Wiki 模式在约 1000 文件以内是正确的，超过后因数据模型而结构性崩坏**（不是提示词、模型或纪律问题）；修复方案是五个可强制的不变量，核心机制一句话："**引文（quote）是指针，不是副本**"（Ted Nelson 1965 年 transclusion 思想的工程化）。
- **方法要点**（README 全文，比 Zenodo 摘要详细得多）：
  - 310 个来源的跨学科调研（信息检索、agent 记忆、档案学、认知心理学）；形式化决策程序：8 个候选架构、锁定权重（一致性比率 0.009）、**20,000 次 Monte Carlo 敏感性扫描**、失败模式分析（严重度打分）、minimax regret、竞争性假设分析；完整决策记录随论文公开。
  - **三个结构性缺陷**：
    1. **wiki 成为它自己的来源（自引用/投毒循环）**：原 gist 明确指示"好答案归档回 wiki 作为新页面" + wiki 与 raw 同索引等权检索 → 摘要的摘要的摘要，每轮有损且**无声**。gist 评论区实测案例：一个从未入库的主题（潜水器 Trieste）返回 **12 个自信的检索命中**——"一个自信的编造被归档成页面之后，它就成了来源"。
    2. **lint 审计一致性，而一致性 ≠ 真实性**：均匀漂移的 wiki 完美通过 lint；lint 从不把 wiki 断言与其源字节比对——"审计系统读的是它自己审计的语料"。
    3. **引文是副本、引用是生成文本**：模型能生成看起来正确、解析到真实文件、读起来合理、但**不支持该断言**的引用；失败模式分析评为 9/9 最高严重度，且**原设计内无解**（无法靠提示词修复）。
  - **证据表**（README 附验证状态，均为一手核实）：
    - ACE 论文 "context collapse"：累积上下文 18,282 tokens / 任务精度 66.7%（第 60 步）→ **一次全量重写后 122 tokens / 57.1%**（第 61 步），低于从不累积的 63.7% 基线。
    - 引用幻觉：商业模型 11–57%；GPT-3.5 生成引用 55% 全虚构、GPT-4 18%（n=636 人工核查）；RAG 也堵不住（临床研究：无 RAG 45.3% 幻觉引用，有 RAG 仍 18.8%）。
    - 长上下文不是逃生门：相关信息位于上下文中段时精度掉 30%+（U 型曲线）；Context Rot 研究（18 个模型含 1M 窗口）：300–400k tokens 处 30–50% 非均匀退化。
    - 链接腐烂：哈佛法律评论 70%+ URL 已失效；2013–2023 网页 1/4 已消失 → raw 层必须存完整档案（WARC/SingleFile），不能只存 markdown + 链接。
  - **五个不变量**（binary gate，用文件系统和工具链强制，永不靠提示纪律）：
    - **I1**：raw/ 不可变、内容寻址（SHA-256）+ 原子出处记录；agent 对 raw 只读（理想为只读挂载）。
    - **I2**：派生文本的**每个字符映射到源坐标**（页码/bbox/媒体时间戳/字符偏移）——整个构建里"诚实的难点"。
    - **I3**：所有索引和 wiki 页都是**可丢弃的派生物**，可从 I1+I2 随时重建，带版本戳；"删不掉重建的东西放错了层"。
    - **I4**：综合层 **append-only 增量 + 有效期区间**：矛盾不覆盖旧断言，而是关闭旧断言 validity interval、开新断言 → 完整保留信念史，免费获得双时间查询（"我三月相信什么、依据是什么"）。
    - **I5**：**单向流，wiki 输出永不被索引为来源**（origin: derived；索引器跳过 + 文件系统分树 + CI 检查三重强制）——切断投毒循环的防火墙。
  - 操作层：ingest（采集廉价无差别，**提升进综合层要门控**——"hoard sources, ration conclusions"）；query（低相关命中时必须回答"语料库没有可靠答案"且**不得归档**该答案）；**verify 取代 lint 的核心角色**（~50 条黄金断言每周 + 每次解析器升级后重解析 selector，解析率 <100% 则**封锁全部综合写入**）。
  - 分阶段上线 + **两天 kill test**（Stage 0：20 个刁钻文档、10 个需精确引用的问题，只测 span 锚定能否存活——失败则说明该跑原版 Karpathy 模式）。
  - **明确的不适用条件**（难得的诚实）：语料 <300–1000 源 + 每页有人工审阅 + 精确引用需求少 → 原版拿约 2/3 价值花 5% 功夫，直接用原版。完整 provenance 构建约 60 人日（已含 2× 拖延系数）。
  - 可逆性分级：R0 不可逆（语料格式/哈希/出处/schema/selector 模型——只用几十年老技术：纯文件/Git/SQLite/Markdown/BM25）＞R1 可逆有迁移成本（解析器/wiki schema/工具面）＞R2 可丢弃（向量库/嵌入/reranker——按月选型随时换）。
- **对我们项目的启示**（本项目最重要的一篇架构批评）：
  1. **"好答案归档回 wiki"必须加防火墙（I5）**：归档的答案只能以"标注为 derived、且每条断言回指 raw span"的形式存在，绝不能进入主检索索引——否则就是慢性自投毒。这是对 Karpathy 原始配方最要命也最可修复的偏差。
  2. **引用机制不能让模型自由生成**——模型不写 selector，工具从字节偏移生成；这直接决定我们 schema 的设计。
  3. lint 之外必须有 **verify**：抽样断言回溯源字节验证，低于阈值封锁写入。
  4. 矛盾处理用 **DEPRECATE/有效期区间**，不用覆盖删除（与 #9 TrajWiki 独立收敛到同一设计）。
  5. 全套 provenance 太重，但我们的目标用户多数处于"<1000 文件 + 人工可审阅"区间——**先做轻量版（I5 防火墙 + 引用规范 + verify 抽查），架构上预留升级路径**，这恰好也是论文自己给出的建议。
  6. index.md 的扩展上限 = 一个上下文窗口的三角化能力；SQLite FTS5 一个文件一小时，无理由等到疼了再加（与 #4 呼应）。

## 第二优先：架构与经济性

### #6 Knowledge Compounding（知识复利的经济分析）

- **来源**：arXiv:2604.11243（econ.EM，v1 2026-04-13，v2 2026-04-15）
- **作者/机构**：Shuide Wen, Beier Ku（Qing Claw：OpenClaw 多 agent 框架的工业级 C# 重实现）
- **一句话结论**：把 LLM token 从**消耗品重新归类为资本品**：引入持久结构化知识层后，任务成本不再相互独立，Cost(t) 由知识库覆盖率 H(t) 驱动——受控四查询实验中 compounding 机制累计耗 47K token vs 匹配 RAG 基线 305K，**省 84.6%**。
- **方法要点**：
  - 在 Agentic ROI 框架（Liu et al. 2026）上指出原成本项隐含"任务成本相互独立"假设——RAG 下成立，持久知识层下失效；提出动态 Agentic ROI 模型。
  - 三个微观机制：(i) 一次性 INGEST 摊销到 N 次检索；(ii) 高价值答案自动反馈进综合页；(iii) 外部搜索结果写回实体页。
  - 声称是首个 Karpathy (2026) LLM Wiki 范式的完整工业级参考实现（约 200 行 C#，确定性种子 42）。
- **关键数字**：47K vs 305K（省 84.6%）；30 天校准投影：中等主题集中度省 53.7%、高集中度省 81.3%，差距随时间**单调扩大**。
- **对我们项目的启示**：
  1. **与 #1 的成本结论表面冲突，实为互补**：#1 是"每次查询 agent 重新浏览 wiki"模式（每查询 21×）；本文是"答案写回 + 后续查询命中已编译知识"模式（省 84.6%）。**查询是否复用已编译成果是成本的决定性变量**——我们的 Query 操作必须把好答案沉淀下来（带 #5 的防火墙），否则复利不存在。
  2. **主题集中度决定收益**：高集中领域省 81.3% vs 中等 53.7%——个人用户深耕少数领域时复利最大；这提示我们的目标场景应是"持续深耕型用户"而非"泛收藏型用户"。
  3. 谨慎引用：4 个查询的实验很小，30 天是校准投影非实测；发在 econ.EM，作者非主流 ML 机构。
  4. 但其"token 资产负债表"的度量框架值得直接抄：每查询 token、ingest 成本、已编译知识命中率——**我们项目应该从第一天就埋这些度量**。

### #7 Retrieval as Reasoning（LLM-Wiki，agent 原生检索）

- **来源**：arXiv:2605.25480（v1 2026-05-25，v2 2026-05-26）
- **作者/机构**：Haoliang Ming, Feifei Li, Xiaoqing Wu, Wenhui Que（该组同时是 #8 WikiLoop、#10 WikiKV 的作者群，系列工作）
- **一句话结论**：检索应当是推理而非单次查询：把外部知识当作**可编译（compilable）、可组合（composable）、可演化（evolvable）** 的结构而非静态索引，agent 经 search/read/链接跟踪工具迭代取证，在多跳 QA 上超 HippoRAG 2 / LightRAG / GraphRAG **2.0–8.1 F1**。
- **方法要点**：文档编译为带**双向链接**的结构化 wiki 页；经标准 tool-calling 接口暴露 search / read / link-following；**Error Book（错误本）** 做持久的结构与语义自纠错（记录失败路径避免重复犯错）。
- **关键数字**：HotpotQA、MuSiQue、2WikiMultiHopQA 上 SOTA（+2.0–8.1 F1）；AuthTrace 上最佳整体准确率，多文档结构化查询优势最大。
- **对我们项目的启示**：
  1. 三原则 Compilability / Composability / Evolvability 可直接作为我们检索层的设计准则（比"RAG vs wiki"的二分更有操作性）。
  2. **Error Book 是性价比最高的自纠错机制**（对比 #3 的 RL）：一个记录"哪里检索失败过、为什么"的持久页面，防止 agent 在同一处反复跌倒——个人项目几小时可实现。
  3. 双向链接 + 工具接口 = "wiki 是 agent 的检索界面"这一核心定位的实证支撑。

### #8 WikiLoop（Builder + Navigator 联合学习）

- **来源**：arXiv:2607.26604（v1 2026-07-29）
- **作者/机构**：Haoliang Ming, Feifei Li, Wenhui Que（同 #7 系列）
- **一句话结论**：知识库构建与查询历来被孤立优化（构建收不到下游信号）；WikiLoop 用角色条件化共享策略把二者耦合：**Builder 的每次编辑由 Navigator 的下游表现评分**，下游反馈让 wiki 越用越好。
- **方法要点**：
  - role-conditioned 共享策略双接口：Navigator 检索证据答题；Builder 提结构化编辑。
  - Navigator 目标：**sufficiency-before-efficiency**（充分性先于效率）——收齐完整证据之后才施加检索成本惩罚。
  - Builder 从**效用差**学习：冻结的 Navigator 给每个候选编辑按"下游表现变化"打分；**guard penalty** 惩罚对无关查询的回归。
  - 训练：角色专属顺序优化 + 角色同质批次上的最终联合阶段。
- **关键数字**：Qwen3.5-9B 骨干；AuthTrace 62.6 aggregate Answer Correctness（超 LLM-Wiki base **+6.3**，多文档查询增益最大）；最终共享策略比对应专家参考在 Navigator/端到端各 +0.4（两角色能力基本保住并合并进一个模型）；无数据集特定训练时也在 HotpotQA/MuSiQue 上超过同骨干 LLM-Wiki base；学到的编辑对 held-out Navigator 仍有用。
- **对我们项目的启示**：
  1. **"构建收到下游信号"是 wiki 模式的正确演进方向**：页面该建/该拆/该合并，应由查询效果驱动——这为 #2 的粒度治理问题提供了答案方向（不是预设规则，而是用查询反馈调节）。
  2. **guard penalty 可规则化为我们的 lint 回归测试**：任何 wiki 编辑前后跑一遍固定问题集，已有正确答案变错即拒绝该编辑。
  3. "充分性先于效率"翻译给我们：先保证证据收齐（质量门槛），再优化 token（#4 的渐进披露）——顺序不能反。
  4. RL 训练不现实，但"编辑效用评估 + 回归守护"两个机制都可以脱离 RL 单独实现。

### #9 TrajWiki（声明级变更操作 + 层级路由）

- **来源**：arXiv:2608.00967（v1 2026-08-02）
- **作者/机构**：Jingyu Sun, Yuyang Xue, Mingyang Li 等 12 人（通讯 Hongpeng Zhou；摘要页未标机构）
- **一句话结论**：长时程对话 agent 的记忆不该是孤立条目或可覆盖状态，而应是**溯源的演化轨迹**：不可变情景快照 + 声明级 ADD / REVISE / DEPRECATE 操作 + Memory Wiki 中间层；LoCoMo 与 MedMT 上跨开源/闭源骨干全面提升。
- **方法要点**：
  - 每条记忆 = 溯源演化轨迹（source-grounded evolution trajectory），以**不可变情景快照**保存。
  - **声明级操作**：ADD / REVISE / DEPRECATE——信息过时**标记弃用而非覆盖删除**，保留"信息如何起源、演化、冲突、过时"的全history。
  - **Memory Wiki**：持久中间层，把对话历史**增量编译**为互链结构页，显式捕捉实体、事件、数量、主题、**冲突**。
  - 推理时**层级路由**：相关 wiki 页 → 链接的记忆轨迹 → 对应快照 → 源消息，做证据接地合成。
- **关键数字**：LoCoMo、MedMT 上长时程对话表现提升（摘要未给具体值）；提供记忆演化、检索失败、答案生成的可解释性与诊断可见性。
- **对我们项目的启示**：
  1. **DEPRECATE 而非删除**——与 #5 的 I4 有效期区间两个独立工作收敛到同一设计，可作为我们断言生命周期的定论：断言从不被抹掉，只被标记过时并指向继任者。
  2. **冲突是一等公民**：wiki 页显式建模"冲突"区块（同一主题下相互矛盾的来源主张并列），而非强行调和——这对知识库可信度至关重要。
  3. 层级路由（wiki → 轨迹 → 快照 → 源）与 #5 的 raw→spans→wiki 分层异曲同工，验证" wiki 是索引层不是真相层"。
  4. 对话记忆与文档知识库两个场景的架构正在收敛——我们若做对话式 ingest，可直接借用其声明级操作集。

### #10 WikiKV（path-as-key 层级存储，微信生产验证）

- **来源**：arXiv:2606.14275（cs.DB，v1 2026-06-12）
- **作者/机构**：Feifei Li, Haoliang Ming, Zihan Li, Hang Liao, Xingyu Fan, Xiaoqing Wu, Chenggong Wang, Wenhui Que（8 人；经**微信公众号 AI 助手**真实部署验证——即腾讯/微信生产环境）
- **一句话结论**：LLM 策展的树状 wiki 已成检索增强应用的主流基底，但其**存储层被当成实现细节**——该工作负载的层级性、查询密集、持续演化三属性需要原生存储模型：path-as-key 的 KV 存储 + 可演化 schema + 无锁一致性协议 + O(1) 预算导航。
- **方法要点**：
  - (i) 数据驱动 schema：**Intent-Anchored Schema Induction** 自举层级 + **Continuous Evolution Operators** 持续精化（schema 不是一次定死）。
  - (ii) 路径索引存储的一致性协议：并发离线重写下**不产生部分读**，读路径无锁。
  - (iii) 预算导航算子：搜索加速路由把 LLM 辅助下降步数**从 d 降到 O(1)**，同时保持 anytime 语义（答案渐进精化）。
- **关键数字**：微信公众号 AI 助手真实部署；AuthTrace 63.2% 端到端答案正确率（超多个 RAG 基线，**低/高扇入多文档问题差距拉大**）；四类查询算子对关系型、图、文件系统后端实现均衡的低单算子延迟；消融确认三组件各自有效。
- **对我们项目的启示**：
  1. **"存储层不是实现细节"**：即便我们用纯 markdown 文件，路径 schema（页面如何命名、层级如何组织）和并发写安全（agent 写入时用户正在读）都必须显式设计。
  2. **path-as-key** 与 #4 的发现（强 agent 从问题直接猜路径）互相印证：**语义化路径本身就是检索界面**——目录结构要按"用户会怎么问"来设计。
  3. **路由从 d 到 O(1)**：索引/路由的搜索加速让导航不再逐层调 LLM——这是查询侧成本（#1 的 21× 问题）的又一工程解，且与渐进披露正交可叠加。
  4. 生产级部署证明该模式可规模化、可运维，不是 toy——对我们选型和说服贡献者都有说服力。

### #11 WiCER（编译鸿沟与 CEGAR 式迭代编译）

- **来源**：arXiv:2605.07068（v1 2026-05-08；CC BY-NC-ND）
- **作者/机构**：Juan M. Huerta（独立研究者；#1 论文的相关工作部分引用了他的另一项 KV-cache wiki 研究）
- **一句话结论**：**编译鸿沟（compilation gap）**是 LLM wiki 的核心风险：盲编译的 wiki 灾难性失败率 53–60%；但 CEGAR 式"编译 → 探针评估 → 诊断 → 强制保留"迭代 1–2 轮即可恢复 80% 质量、灾难失败率相对降 55%。
- **方法要点**：
  - 场景：wiki 编译后以 **KV cache 全上下文**服务（亚秒延迟、零检索失败）。
  - 17 个 RepLiQA 域、6,800 问题刻画编译鸿沟；WiCER 借鉴**反例引导抽象精化（CEGAR）**：诊断探针评估编译产物 → 定位被丢弃的事实 → 下轮编译强制其保留。
- **关键数字**：
  - 全上下文 KV cache 4.38 vs RAG 4.08（满分 5），TTFT 快 7.3×——但**规模化后因注意力稀释（attention dilution）退化到低于 RAG**。
  - 盲编译：2.14–2.32 vs 3.46，**灾难性失败率 53–60%**。
  - WiCER 1–2 轮迭代：3.24（vs 原始全上下文 3.47，15 个有基线主题），恢复 80% 丢失质量，灾难失败率 **-55%（相对）**。
  - 消融：**定向诊断 +0.95 vs 通用 pinning +0.16**——收益来自找具体丢失点，不是一刀切"多保留"。
- **对我们项目的启示**：
  1. **编译必有损，"compile once" 不够，需要 "compile → probe → refine" 回路**：我们的 ingest 管线应内置诊断探针（对每源生成若干"应能答出"的问题，编译后验证，丢了的强制补回）。
  2. 注意力稀释 + #5 的 Context Rot：**"全部塞进上下文"不是出路**，结构化导航（#4/#10）才是。
  3. 定向诊断 >> 通用保留：修复 wiki 要定位具体丢失点，"让模型多写点"没有用。
  4. KV cache 服务是 wiki 的另一种 serving 形态（被预填充而非被浏览），适合小规模高频域，规模大后退化。

### #12 Beyond Memory（append-only 模板与负面结果保留）

- **来源**：arXiv:2607.24759（v1 2026-05-29）
- **作者/机构**：Priscila Saboia Moreira, Christopher R. Sweet（2 人，摘要页未标机构；直接引用 Karpathy 2026 gist 与 tonbi 2026）
- **一句话结论**：llm-wiki-memory-template 是异质协作知识工作的**基底（substrate）**：多人类 / 多 AI agent / 多领域三轴各有架构元素支撑；**append-only 约定保留死胡同与负面结果**——这是出版物和代码共享在结构上无法解决的"负面结果丢失问题"。
- **方法要点**：
  - 三个部署案例 + 一个设计报告：单人研究谱系（保留被放弃的迭代）；双作者项目（**回溯审计把先前实验声称的 20/20 覆盖修正为 14 和 12，修复后 18 和 18，失败路径全程保留在制品中**）；进行中的多 agent 部署（作为设计报告）；跨领域教育变体。
  - 命名三个横切社会技术属性：**失败路径保留（failure-path preservation）、agent 诚实（agent honesty）、挪用（appropriation）**。
- **对我们项目的启示**：
  1. **"被放弃的想法也有复利价值"**——避免重走死路是知识库对普通用户最有说服力的卖点之一；append-only 不只是 log.md 的格式约定，是价值主张。
  2. **agent 诚实**：wiki 应记录 agent 自己的失败、不确定与修正，而非只存光鲜结论——这提高整个系统的可信度。
  3. 回溯审计案例（20/20 → 14/12 → 18/18）展示了 wiki 让"审计自己曾声称的东西"成为可能——**可审计性本身是功能**。
  4. 模板化（可直接复制的 repo 结构 + schema）是该模式扩散的正确形态，也正是我们项目要提供的东西。

### #13 Streaming Knowledge Compilation（物性评分 φ_t 与流式预算）

- **来源**：arXiv:2606.09877（v1 2026-06-03）
- **作者/机构**：Juan M. Huerta（与 #11 同一独立作者，系列工作）
- **一句话结论**：流式场景下"什么值得进缓存预算"可形式化为对完美先知 oracle 的**累计遗憾最小化**：物性评分 φ_t(k,n)∈[0,1] 作为查询相关性代理做主动 pinning，证明 O(√(T·log K)) 遗憾界；并揭示 **LLM-as-judge 在训练后知识上存在系统性混淆——遗憾分析而非绝对 QA 分才是可靠评估指标**。
- **方法要点**：
  - 形式化设定：文档流 + 固定 token 预算 + 摄入时未知的未来查询；ε = E[‖φ_t − φ̂_t‖] 是唯一领域相关量。
  - 双域实例化：金融——冻结 Llama 3.1 8B 分类头预测异常波动率；Wikipedia——Abnormal Edit Ratio（AER，截面归一化的编辑速度）。
- **关键数字**：
  - 金融：AUROC 0.728（76K 文章、严格时间分割）；被预测为"重要"的文章实现 1.49× 前向波动率；累计遗憾收敛到 -20.0（-0.12/步）。
  - Wikipedia：+16.0（+0.13/步）——**正号证实 Wikipedia 编辑内容确为训练后知识**（更丰富的上下文稳定提分：No Wiki 3.80 vs Oracle 4.74），以此消除 judge 混淆。
  - 评估规模：173（金融）/ 119（Wikipedia）匹配对。
- **对我们项目的启示**：
  1. **"什么值得入库"是可形式化的预算分配问题**：个人用户的信息流（RSS/稍后读/文章）不能见什么存什么——需要 materiality 信号；领域信号可迁移（金融用波动率、wiki 用编辑速率，个人库可用"重复出现频率/跨源提及"）。
  2. **LLM-as-judge 混淆的警告对我们的评估设计是红线级**：judge 模型可能本来就（不）知道答案，知识库的"增益"必须用同域对照（有无 wiki 的差分）度量，绝对分无意义。
  3. 与 #11 构成同一作者的两部曲：#11 修编译质量，#13 修流式预算——合起来是"持续保鲜"的学术框架。

### #14 AutoSci（SciMem：schema 治理的研究记忆）

- **来源**：arXiv:2605.31468（v1 2026-05-29；代码 github.com/skyllwt/AutoSci）
- **作者/机构**：Weitong Qian, Beicheng Xu 等 19 人（北京大学，崔斌 / 缪雪峰组）
- **一句话结论**：科研全生命周期的记忆中心 agent 系统：SciMem 提供 **schema 治理**的研究记忆（长期科学知识 vs 活跃项目制品分离），SciEvolve 把四类反馈转化为对记忆组织、技能、模板的**版本化更新**——一个可跨项目执行、记忆、演化的持久研究环境。
- **方法要点**：
  - **SciMem**：长期知识记忆（可复用科学知识）与活跃研究记忆（想法/实验/手稿/评审等项目级 artifacts）**分离**。
  - **SciFlow**：五阶段生命周期（文献理解 → … → rebuttal），harness 统一控制状态、上下文、验证、反馈、编排。
  - **SciDAG**：DAG 形多 agent 算子 + 可复用阶段模板增强困难技能。
  - **SciEvolve**：用户/实验/评审/环境反馈 → SciMem 组织、SciFlow 技能、SciDAG 模板的版本化更新。
- **关键数字**：摘要未给定量结果（系统型论文）；代码开源。
- **对我们项目的启示**：
  1. **"长期知识 vs 活跃项目制品"分离**直接适用：用户的稳定主题页（wiki 本体）与进行中项目笔记（工作区）应是两块存储 + 不同的 schema 与生命周期，不混在一个 wiki 里。
  2. **schema 治理（governed）而非 schema 提示（suggested）**：结构约束要有验证器兜底——呼应 #5 的"用工具链强制而非提示纪律"。
  3. SciEvolve 的"反馈 → 版本化更新"把 lint/维护从纠错重构为持续演化——我们的维护回路可以借用这个框架描述。
  4. 科研场景对我们过重，但 memory / flow / operators / evolve 的模块划分是个人项目很好的参考架构切面。

## 交叉综合（Cross-Cutting Synthesis）

### 主题 A：成本之争——"wiki 到底省不省 token"

| 论文 | 结论 | 设置 |
|---|---|---|
| #1 Cochran | wiki 每查询 **21×** token，无回本点 | agent 自由浏览 wiki，无答案写回，24 篇小语料 |
| #6 Wen & Ku | compounding 省 **84.6%** | 答案写回 + 后续命中已编译知识，30 天投影 |
| #4 Cochran | 渐进披露全面降成本、质量不降 | 709 页，目录+摘要+按需打开 |
| #10 WikiKV | 路由把 LLM 下降步数 d → O(1) | 生产部署，搜索加速路由 |
| #11 WiCER | KV cache 亚秒但规模化后注意力稀释 | 全上下文预填充 |

**调和**：wiki 的查询成本由三个杠杆决定——(a) 查询路径设计（渐进披露/路由/语义化路径），(b) 已编译知识复用率（答案沉淀 + 防火墙），(c) serving 方式（agent 浏览 vs 预填充）。#1 的负面结果发生在三个杠杆全没拉的设置下；三个杠杆均有论文证明有效且**可叠加**。我们项目应把"每查询 token"作为北极星指标之一，从第一天埋点。

### 主题 B：结构性衰减——一致收敛的证据链

- #2（撤稿）：fragmentation / atomization / over-merging（页面粒度退化）
- #3：不完整 / 不正确 / 冗余，**迭代使用中复合放大**
- #5：自引用投毒循环 / 一致性≠真实性 / 生成引用不可救药，**~1000 文件阈值**（社区观察，非受控研究）
- #11：编译鸿沟——盲编译灾难性丢事实 53–60%
- #12（引用 Memory as Metabolism, arXiv:2604.12034）：用户耦合漂移、认知卸载、知识库硬化（Kuhn 问题）

**结论**：衰减不是边缘问题而是模式的核心风险。缓解手段已在多篇独立工作中收敛：**单向流防火墙**（#5 I5）、**声明级版本化/弃用**（#9 ADD/REVISE/DEPRECATE ≈ #5 I4 有效期区间）、**查询驱动修复**（#3 诊断-定位-修复、#8 下游效用评分）、**验证回路**（#5 verify 抽样回溯、#11 CEGAR 探针）、**Error Book**（#7 轻量自纠错）。我们项目应全部纳入设计。

### 主题 C：评估方法论危机（引用任何数字前必读）

- #1：双裁判在整体 groundedness 上排名一致性 **rho=0.04**；自动评分器 vs 人类标注一致率 65–69%（未达预设规则）；作者**自己撤回过一次 v1/v2 结论**（截断 bug）。
- #2：整篇**撤稿**。
- #4：人工评分者与模型裁判一致性远低于计划要求，质量结论只能依赖裁判。
- #13：LLM-as-judge 在训练后知识上有**系统性混淆**，绝对 QA 分不可靠。
- #6：4 查询小样本 + 30 天校准投影。
- 推论：**预注册（#1/#4）、人类标注校验（#1）、同域对照/遗憾式评估（#13）是本领域目前仅有的可靠做法**。我们若要对外宣传效果数字，评估设计必须至少做到同域差分 + 人工抽检，且诚实报告置信区间。

### 主题 D：分层架构的收敛

多篇独立工作收敛到同构分层：
- #5：raw（不可变，内容寻址）→ spans（每字符带源坐标）→ index（可丢弃、版本戳）→ wiki（append-only、有效期）
- #9：源消息 → 快照 → 轨迹 → wiki 页（层级路由）
- #10：层级 KV + 可演化 schema + 一致性协议
- #14：长期知识记忆 / 活跃研究记忆分离
- #11：编译 → 探针 → 精化（编译层自校验）

共同原则：**不可变的真相层 / 可重建的派生层 / 版本化的声明层 / 单向的数据流**。这是我们架构设计的直接蓝本。

### 主题 E：研究空白 = 我们的机会

1. **面向普通用户（非研究者、非 agent）的可用性研究为零**——所有论文要么 agent 导航（#7/#8/#10），要么研究者自用（#1/#4/#5/#12）。Karpathy 模式的本意（人机协同、人读 LLM 写）在学术侧几乎未被研究。
2. 中文/多语言个人知识库：未见专门工作。
3. 隐私/本地优先：仅 #5 把 "fully local, self-hostable" 作为硬性门槛。
4. 人机 curation 工作流（人筛选来源、把关结论）：#12 触及（human-owned synthesis boundary）但未系统化。
5. 小规模（<300 源）下的最简正确实现与工具化：#5 明说这个区间原版就够，但没人做工具支持——**恰是我们的定位空间**。

## 对本项目的行动建议汇总（供设计阶段讨论）

1. **架构采纳分层四层**（#5/#9/#10 收敛）：不可变 raw → 带 source 坐标的中间层 → 可丢弃索引 → append-only wiki；引用用工具生成的指针/锚点，模型不得自由生成引用。
2. **"好答案归档"必须加防火墙**：归档答案标注 origin: derived、排除出主索引、断言回指 raw span（#5 I5 + #6 机制 ii 的安全版）。
3. **断言生命周期用 ADD/REVISE/DEPRECATE + 有效期**，矛盾显式建模不强行调和（#9 + #5 I4）。
4. **index.md 三级渐进披露**（目录 → 单行摘要 → 按需打开）+ 语义化可预测路径（#4 + #10）。
5. **维护四件套**：lint（一致性）+ verify（抽样回溯源字节，低于阈值封锁写入）+ Error Book（失败路径记录）+ 回归守护（编辑前后固定问题集不变错）（#5/#7/#8）。
6. **ingest 带探针**：每源生成"应能答出"的诊断问题，编译后验证，丢失强制补回（#11 CEGAR）；同时引入 materiality 信号做入库预算（#13）。
7. **成本从第一天埋点**：每查询 token / ingest 成本 / 已编译知识命中率三个指标（#6）；查询路径优先"命中已编译知识"，其次渐进披露，避免 #1 式自由浏览开销。
8. **评估用同域差分 + 人工抽检**，绝不引用绝对 LLM-judge 分数做对外宣传（主题 C）。
9. **页面粒度治理**写入 schema（何时开新页/拆分/合并），lint 查 fragmentation/atomization/over-merging 三方向（#2，注意其已撤稿）。
10. **产品定位落在空白区**：<1000 源、普通用户、本地优先、人机 curation 工作流工具化（主题 E）——学术侧没人做，恰好是 Karpathy 模式对普通人的承诺。
